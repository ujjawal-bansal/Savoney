# Deploying Savoney

Two supported setups. Both keep the browser on a **single origin**, which is
what lets the `httpOnly` refresh cookie work at all.

| Setup               | Client             | API           | Config        |
| ------------------- | ------------------ | ------------- | ------------- |
| **All Render**      | Render Static Site | Render Docker | `render.yaml` |
| **Vercel + Render** | Vercel             | Render Docker | `vercel.json` |

The API stays on Render either way: it is a long-running Express server with a
Mongoose connection pool, in-memory rate limiting and lazy recurrence
materialisation. Running it on Vercel's serverless functions would need
per-invocation connection caching and an external rate-limit store, so it is
not a drop-in.

Vercel is the better host for the _client_: a global CDN with no cold start,
where a Render free web service sleeps after 15 minutes idle. Its `rewrites`
proxy `/api/*` to the Render API, so the browser still sees one origin and the
cookie stays first-party.

Everything below covers the all-Render path. For Vercel, do steps 1 and 2 to
get the API up, then instead of the Render static site:

1. [vercel.com](https://vercel.com) > **Add New** > **Project** > import this repo
2. Vercel reads `vercel.json`; leave every setting at its default
3. **Update the rewrite destination in `vercel.json`** if Render assigned your
   API a hostname other than `savoney-api.onrender.com`, then push
4. On the Render API, set `CORS_ORIGINS` and `APP_URL` to your Vercel URL

## Deploying to Render

Two services from one repo: a Dockerised API and a static client, with MongoDB
Atlas for data. Everything below fits in free tiers.

---

## 0. Rotate the leaked credentials first

`server/.env` was committed in an early commit that is **already public on
GitHub**. It contained a live Atlas connection string and the original
`JWT_SECRET`. Anyone who has read the repo has both.

The v2 app no longer uses that `JWT_SECRET` at all, so it is already dead. The
database password is not.

1. Atlas > **Database Access** > edit the user > **Edit Password** >
   **Autogenerate Secure Password** > **Update User**
2. Atlas > **Network Access** > confirm the allowlist is what you expect

Do this before deploying. The strings stay in git history; rotation is what
makes them worthless.

---

## 1. MongoDB Atlas

1. Create a free **M0** cluster.
2. **Database Access** > add a user with _Read and write to any database_.
   Use the generated password.
3. **Network Access** > **Allow access from anywhere** (`0.0.0.0/0`).
   Render's outbound IPs are not static on the free tier, so an allowlist of
   specific addresses will break. The database is still protected by
   credentials and TLS.
4. Copy the connection string and append the database name:

   ```
   mongodb+srv://USER:PASSWORD@cluster.xxxxx.mongodb.net/savoney?retryWrites=true&w=majority
   ```

   URL-encode the password if it contains `@ : / ? # [ ] %`.

---

## 2. Deploy both services

1. Push this branch and open a PR, or merge to `main`.
2. Render Dashboard > **New** > **Blueprint** > select this repository.
3. Render reads `render.yaml` and creates **savoney-api** and **savoney-web**.
4. It will prompt for the two secrets that are deliberately not in the repo:

   | Variable    | Value                                                      |
   | ----------- | ---------------------------------------------------------- |
   | `MONGO_URI` | The Atlas string from step 1                               |
   | `SMTP_URL`  | See step 4. Required: the API refuses to start without it. |

   `JWT_ACCESS_SECRET` and `JWT_REFRESH_SECRET` are generated by Render.

5. First build takes 5–10 minutes. The API is ready when `/api/ready` returns
   `{"status":"ready","database":true}`.

### If Render assigns different hostnames

Blueprint names are taken globally, so you may get `savoney-api-a1b2`. If so,
update three values in the dashboard and redeploy:

- **savoney-web** > Redirects/Rewrites > the `/api/*` destination
- **savoney-api** > Environment > `APP_URL` and `CORS_ORIGINS`

---

## 3. Why the client proxies the API

`savoney-web` rewrites `/api/*` to the API service, so the browser only ever
sees one origin.

This is not cosmetic. The refresh token is an `httpOnly` cookie with
`SameSite=Strict`. Served from a second host it would be a _cross-site_ cookie,
and browsers do not send strict cookies cross-site: every page reload would
silently sign the user out, with no error to explain it.

**If you ever serve the client from a different host** (a custom domain on the
client but not the API, say), you must also:

1. Set `COOKIE_SAMESITE=none` on the API. The app validates this and refuses to
   start unless `APP_URL` is `https://`, because browsers ignore `SameSite=None`
   on a non-Secure cookie.
2. Set `CORS_ORIGINS` to the exact client origin, scheme included.

`SameSite=None` is safe here: the API authorises by `Authorization` header
only, never by cookie, so a cross-site request can trigger a refresh but cannot
read the response past CORS.

## 4. Email for password resets (optional, add later)

Skip this to get deployed, and come back to it.

Without `SMTP_URL` the app runs normally and `/api/auth/forgot-password`
answers 503 with a clear message. It does not pretend to send an email, and it
does not stop the deployment.

Any SMTP provider works. Free options with a sender identity:

| Provider | Free tier    | `SMTP_URL`                                              |
| -------- | ------------ | ------------------------------------------------------- |
| Resend   | 3,000/month  | `smtps://resend:API_KEY@smtp.resend.com:465`            |
| Brevo    | 300/day      | `smtps://USER:KEY@smtp-relay.brevo.com:587`             |
| Gmail    | Personal use | `smtps://you@gmail.com:APP_PASSWORD@smtp.gmail.com:465` |

Gmail needs an **App Password** (Google Account > Security > 2-Step
Verification > App passwords), not your account password.

Also set `MAIL_FROM` to an address the provider has verified, or mail will be
rejected or land in spam.

## 5. Seed the demo account (optional)

Recruiters should not have to sign up to see the app work.

Render free-tier Docker services have no shell, so run it locally against the
production database:

```bash
MONGO_URI="<your Atlas string>" npm run seed
```

Creates `demo@savoney.app` / `savoney-demo-2026` with a year of history,
budgets in every state and part-funded goals. Re-running resets it.

Put those credentials on the sign-in page (they are already shown there) so
anyone can look around.

## 6. Verify the deployment

```bash
API=https://savoney-api.onrender.com
WEB=https://savoney-web.onrender.com

curl -s $API/api/health          # {"status":"ok",...}
curl -s $API/api/ready           # {"status":"ready","database":true}
curl -s $WEB/api/health          # same, proving the rewrite works
```

Then in a browser, and this order matters:

1. Sign in as the demo user
2. **Reload the page.** You must stay signed in. If you are bounced to the
   sign-in screen, the refresh cookie is not reaching the API: re-read step 3.
3. Add a transaction, confirm the dashboard totals move
4. Request a password reset and confirm the email arrives

## Known limits of this setup

- **Free instances sleep** after 15 minutes idle. The first request then takes
  30–60 seconds. Fine for a portfolio; not for real users.
- **Rate limiting is per-process.** One instance today, so it works. Scale to
  two and the limits become advisory: move the counter to Redis first.
- **No error tracking or backups.** You will hear about outages from users, and
  Atlas M0 has no automated backups.
- **Free Atlas is 512 MB**, which is tens of thousands of transactions.

---

## Rolling back

Render keeps every deploy. Dashboard > service > **Events** > pick the last
good deploy > **Rollback**. Roll the API back before the client if a change
spans both.
